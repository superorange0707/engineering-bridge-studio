# Architecture

This document describes the original V1 behavior plus the current development collaboration path.

## Durable collaboration execution

`CollaborationRunService` is a separate path for ChatGPT Web's engineering/research contracts. It uses the existing Codex executor's `workspace-write` mode in a unique private workdir, with network off and a deadline. Its manifest is outside the writable workdir and retains the bounded contract, source input hashes, executor metadata/evidence, declared output hashes and Web review. A restart marks unfinished runs interrupted without replay; new contracts link to reviewed parent runs. File hashes establish artifact identity, not scientific validity. The source workspace's controlled-write policy is unchanged: opt-in to isolated execution is a separate `collaboration.execution_workspace_ids` list. The six tools and workflow are described in [tools](tools.md) and [the collaboration guide](chatgpt-codex-workflow.md).

The MCP initialization instructions explicitly place research, planning, outlining, writing and evidence review in ChatGPT Web, and bounded execution in Codex. A local MCP plugin alone does not connect ChatGPT Web. An authenticated remote connection/tunnel must deliver the same STDIO tool surface, and its actual Web round trip must be verified independently from local tests.

## Original V1 paths

Engineering Bridge is a local STDIO MCP server with nineteen tools and a small layered structure:

1. `src/mcp-stdio.ts` recovers any durable control-plane transaction before parsing trusted version-3 workspace configuration or loading persistent workspace state, then registers nineteen tools and connects the MCP STDIO transport.
2. `repository-identity.ts` canonicalizes any project directory and gathers local filesystem identity plus optional Git evidence without a model or network call. `codex-project-references.ts` parses only `projects.<path>` sections from Codex `config.toml` and refuses every other filename, including `auth.json`. `RegisteredWorkspaceRegistry` maps stable caller-visible IDs to current paths. `ManagedWorkspaceCatalog` persists directory/Git type, identity evidence, aliases/path history, permission policy, and source to `$STACK_ROOT/state/workspace-registry.json` with atomic 0600 writes, while reserving `$STACK_ROOT/state/<workspace-id>/` for durable project context, plans, decisions, handoffs, and bounded filesystem-APPLY recovery records. A dependency-free control-plane transaction helper coordinates reviewed config/registry migrations through exact payload hashes, a durably synced `COMMIT_INTENT`, same-directory replacements, idempotent startup roll-forward, and a writer lock shared with catalog persistence. `WorkspaceOnboardingService` auto-onboards valid narrow Codex references only when trusted configuration enables that source, independently auto-onboards valid directories inside explicitly approved managed roots, upgrades directory identity when Git later appears, creates repositories only after exact `CREATE`, grants managed controlled-write permission only after exact `AUTHORIZE`, and reconciles missing paths on attach/use/explicit refresh.
3. `RegisteredWorkspaceTaskService` assigns UUID task IDs and holds task, supervisor-review, thread, output, partial-output, error, and evidence state in process memory. It resolves the requested executor through an `ExecutorFactory` and drives `CodexExecutor` or `DshExecutor`.
4. `codex-routing.ts` selects a capability-oriented logical role without knowing model IDs; `codex-model-registry.ts` is the single generation-specific mapping. `CodexExecutor` starts the local `codex app-server --stdio` protocol with fixed read-only task settings, validates the complete registry against a fresh hidden-inclusive `model/list`, pins the selected exact model plus `max`/`concise` on thread and turn requests, and rejects thread/model mismatch. `DshExecutor` starts the official headless `dsh` interface with a per-process `DSH_PERMISSION_MODE=read-only` pin and an explicit environment allowlist (including `DEEPSEEK_API_KEY` and `DSH_TOOLS_MODE`; proxy variables excluded). `ControlledPatchService` records proposal and routing/model/version/thread metadata (persisted to `<config>.controlled-patches.json`), preserves the existing fixed clean-Git APPLY backend, and uses one strict bounded exact-preimage filesystem backend for registered non-Git directories or Git top-levels with a clean index and unstaged tracked work.

The Bridge core has no public HTTP server, account system or general command runner. A private local daemon owns state; independent MCP sessions reach it through a same-user Unix socket. The companion Launcher separately owns the Web browser and provider transport.

## Read-only supervised task flow

`run_task` is always read-only and accepts an optional `executor: "codex" | "dsh"` (default `codex`). Codex defaults to automatic routing; the advanced `routing` override accepts only `implementer`, `local_lead`, or `repo_principal`, while DSH rejects routing/handoff fields. The registry currently maps those roles to the exact suffixed GPT-5.6 models with `max` reasoning and `concise` summary. Automatic routing chooses `repo_principal` for high-risk/architectural signals, `implementer` only for clearly bounded implementation, and `local_lead` when uncertain. Codex runs with approval `never`, a read-only sandbox policy, and network access disabled. The Codex executor starts native app-server threads with `thread/start`; after supervisor feedback it preserves the selected role and returned thread ID and uses `thread/resume`, followed by a new turn. A cross-role escalation/de-escalation is a separate linked task/thread with `parent_task_id` and a bounded state/evidence snapshot, never an in-place model mutation. The DSH executor runs each task as a headless invocation; it has no machine-resumable session seam, so a DSH `continue` is a new execution and no thread id is fabricated.

`task_result` reports `queued` or `running` with `ready: false`. A successful turn moves to `waiting_for_supervisor_review` with `ready: true` and `review_output`. The response also includes the fixed `executor`, a real native `thread_id` when one exists (Codex only), the bounded, process-local `evidence` collected from command-execution and file-change protocol items, and `partial_output` when a genuine interrupt produced real partial output (the task still ends `failed`). Evidence is diagnostic task output, not authorization to write or proof that a requested semantic result is correct; when existing bounds truncate or evict evidence, explicit markers (`[truncated]`, changes-omitted counts, an `evidence-drop` item) make the incompleteness visible.

`control_task` supplies the supervisor transitions. `continue` requires a non-empty instruction while waiting for review and resumes the same Codex thread for another read-only turn (DSH: a new headless execution). `steer` requires a non-empty instruction while a turn is running and sends it to that turn (Codex only). `interrupt` is valid only while running; an interrupted turn ends in `failed`, not in a resumable review state. `accept` is valid only while waiting for review and promotes the reviewed output to `completed` as `output`.

Active task supervision state (tasks, threads, evidence, review outputs) is process-local and disappears on restart. Controlled-patch proposals/applied history and stable workspace identity state persist across restarts. There is no automatic timeout, automatic acceptance, or persistent task/audit history.

These executor parameters restrict writes performed by Codex and DSH, but Bridge does not create OS-level filesystem read containment. A same-user executor process may read paths outside the workspace when the operating system permits it.

## Controlled patch flow

Controlled writes are a separate path. `generate_controlled_patch` and `refine_controlled_patch` use automatic routing by default and are read-only proposal flows available in any registered workspace; no write authorization is required. Clean Git generation retains the existing base-HEAD unified-diff behavior. If a Git top-level has unstaged tracked work and an unchanged index, generation returns strict complete JSON `modify`/`create` operations whose preimages are exact current-worktree bytes; deletes/renames remain unsupported. Directory generation uses the same operation schema and additionally supports `delete`. Refinement creates a linked new task/thread and bounded handoff snapshot against the same Git base or filesystem preimages. Proposals persist requested routing, logical role/reason/transition, model/effort, Bridge/Codex versions, thread/workspace IDs, backend base, and executor alongside applied history in `<config>.controlled-patches.json`; invalid retained records are quarantined without blocking startup, while replay/applied ambiguity and global invariants fail closed.

`apply_controlled_patch` is the single controlled-write checkpoint: it requires controlled-write permission, exact case-sensitive `APPLY`, and a known completed one-use proposal. Clean Git proposals retain the original base/path validation and fixed shell-free `git apply --check`/`git apply` behavior. Dirty-Git proposals require the same HEAD and a clean index, validate target HEAD/index entries, and reuse the bounded filesystem engine without any Git mutation. Exact-preimage proposals canonicalize every parent/target, reject traversal/absolute/symlink/outside/non-regular/stale paths, and revalidate immediately before each operation. A bounded mode-0600 recovery/audit record is persisted under `$STACK_ROOT/state/<workspace-id>/controlled-patches/` before modification; replacement is atomic, creation is atomic no-clobber, and a partial failure attempts an after-hash-guarded rollback. No backend initializes Git, tests, stages, commits, resets, stashes, cleans, checks out, pushes, publishes, or deploys.

The generation prompt asks the executor for a narrow valid diff, but prompt compliance is not a security boundary. Patch validation is code-enforced; whether the proposed semantic change is desirable remains a human review decision.

## Workspace identity and reconciliation

A logical workspace is not identified by its folder name, current path, or Git alone. Its UUID remains stable while `current_path`, aliases, path history, and optional Git evidence can change. A first-class directory workspace upgrades in place after `git init`, preserving UUID, permissions, and `$STACK_ROOT/state/<workspace-id>/`. Multiple logical workspaces can share one physical Git top-level by carrying different `logical_root` values, so monorepos do not require a new identity design.

Approved configuration seeds are one-time human authorizations. A new valid, narrow, unambiguous, non-excluded Codex project reference becomes an onboarding signal only when trusted configuration enables `codex_projects.auto_onboard`, and then inherits the configured `permission_policy.allow_write`; this controls eligibility only and does not bypass proposal review or exact `APPLY`. When disabled, Codex metadata remains available for existing-workspace diagnosis and reconciliation but cannot admit a new workspace. Managed roots are an independent onboarding source for projects not yet in Codex metadata and retain their configured policy. Broad/missing/unsafe/ambiguous references fail closed. Project Brain is handled as a normal candidate with no repository-name or remote special case.

When a recorded path is missing, reconciliation checks updated safe Codex project references first, then scans only approved managed roots, skipping symlinks and bounded high-volume directories. It compares high-confidence filesystem identity and optional Git identity evidence; a unique match rebinds the existing UUID and records the old path, while no match, multiple matches, an exclusion, or an unsafe destination fails closed. Folder names and root commits alone are never high-confidence identity. There is no workspace watcher: reconciliation runs on attach, use, Bridge/Web workspace request, or explicit `refresh_workspace_registry`.
