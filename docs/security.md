# Security design

The development collaboration path additionally permits bounded engineering/research execution in separate writable run directories. Trusted configuration must opt in source workspace IDs via `collaboration.execution_workspace_ids`; source-project APPLY authorization is separate. Manifests live outside writable workdirs; declared file paths, sizes and hashes are checked. Unfinished runs are marked interrupted on restart without replay. Artifacts are shared with the Web reviewer and hashes do not certify scientific validity. See [the security policy](../SECURITY.md). Original task/patch controls below apply to those paths.

This document separates enforced behavior from operating assumptions for Engineering Bridge Studio. The original task and patch controls are inherited from Bridge V1.

## Shared local service

STDIO entry points connect to one local owner per canonical configuration through a private Unix socket. Each client gets a separate MCP session. Private owner metadata and a token/nonce handshake prevent accidental attachment to a different service; this does not isolate mutually hostile processes running as the same OS user. Clients verify configuration and runtime identity and refuse incompatible live owners. A read-only session cannot gain write capabilities when another session upgrades the shared owner. Executor children carry a marker that prevents recursive Bridge delegation.

The owner exits after its last session disconnects and its active work finishes. A new owner recovers durable collaboration manifests without replaying interrupted experiments. Web caller authentication remains the responsibility of the tunnel and the Web account; the Unix socket is not exposed as a public network endpoint.

## Enforced in code

- MCP callers select only workspace IDs loaded from trusted startup configuration or registered through approved managed onboarding.
- Workspace discovery, canonicalization, optional Git identity matching, onboarding, and path reconciliation use deterministic local filesystem/Git operations only. The Codex metadata reader accepts only `config.toml` and never reads `auth.json`. These paths do not invoke Codex, DSH, or another model and do not enable network access.
- `workspace_diagnostics` is a non-mutating status surface. It distinguishes existing approved/managed workspace usability from onboarding boundary eligibility and controlled-proposal readiness. A dirty proposal precondition never turns a healthy identity into a re-registration recommendation, and `bind_project` is not a universal health check.
- `run_task`, continued turns, steering, and controlled-patch generation use read-only executor execution. Codex defaults to automatic capability-oriented routing; callers can override only a logical role, never a model or effort. The complete central model registry is dynamically validated through hidden-inclusive `model/list`, and every configured model must support `max`; missing capability and thread/model mismatch fail closed. Cross-role handoffs create a linked new task/thread with a bounded state/evidence snapshot instead of changing an existing thread's model. Codex app-server is started without a shell through `codex app-server --stdio`, with approval `never` and network access disabled. DSH rejects Codex routing/handoff fields and runs through the official headless interface with `DSH_PERMISSION_MODE=read-only` pinned per process; the pin cannot be overridden by the host environment, and only an explicit environment allowlist (including `DEEPSEEK_API_KEY` and `DSH_TOOLS_MODE`) is forwarded. Proxy variables are never forwarded.
- Supervisor actions are state checked: `continue` and `accept` require `waiting_for_supervisor_review`; `steer` and `interrupt` require `running`; instructions for `continue` and `steer` must be non-empty. Interrupt completion ends the task as `failed`.
- `partial_output` is returned only from a genuine interrupted executor result; the task state stays `failed`, and ordinary failures never re-expose stderr or partial stdout.
- Codex evidence stays within its existing bounds (string length, changes count, total entry count); truncation and eviction are made visible through explicit markers rather than silently dropped. Markers indicate incomplete diagnostic information, not a complete transcript.
- `allow_write` is a per-workspace controlled-APPLY ceiling, not ordinary direct-write permission. Approved development candidates and managed roots may set it true; ordinary tasks and proposal generation remain read-only. Managed workspaces may also grant it through `authorize_workspace_write` with exact `AUTHORIZE`, which never modifies an approved registration.
- Controlled proposal generation and refinement are read-only and require no write authorization. Clean existing/unborn Git bases retain the unified-diff backend. A Git top-level with a clean index and unstaged tracked work uses strict exact-current-worktree-preimage `modify`/`create` operations; staged/index state and delete/rename operations fail closed. Directory proposals enumerate strict `create`/`modify`/`delete` operations and exact SHA-256 preimages. No proposal changes files or initializes Git.
- Project-instruction preparation reads only bounded ordinary root entries/manifests plus existing ordinary `AGENTS.md`/`PLANS.md`. It generates portable evidence-derived target bytes and preserves all bytes outside one versioned Bridge-owned block. Current evidence replaces only that block; malformed, duplicate, nested, or unsupported ownership markers fail closed. Portability/secret/symlink/size conflicts also fail closed, and the existing controlled proposal/APPLY path is unchanged. Postimage review requires exact target-byte equality; package scripts and Make targets are the only commands inferred automatically.
- Application requires exact, case-sensitive `APPLY`, a completed one-use proposal, and controlled-write permission. The workspace type is re-resolved deterministically, so a directory proposal fails closed if Git appeared and later proposals automatically use the Git path.
- The clean Git path is unchanged: it rechecks the canonical root/base, accepts tracked-file modifications and absent exact-100644 text additions (unborn: additions only), rejects deletes/rename/copy/binary/mode/executable/symlink/submodule/unsafe/duplicate/malformed patches, and invokes only fixed `git apply --check` and `git apply`. The dirty-worktree path requires the same HEAD and a clean index, permits only tracked regular-file modification or absent-file creation, binds every modified target to exact current bytes, and revalidates target/index/root immediately during APPLY. It never touches unrelated tracked/untracked work or invokes Git mutation commands.
- The directory path rejects absolute/traversing/non-normalized paths, symlink targets or parents, outside-root targets, duplicate operations, malformed schemas, stale SHA-256 preimages, non-regular targets, and proposals beyond fixed operation/byte bounds. It persists bounded mode-0600 preimages before mutation, revalidates immediately before each operation, uses atomic replacement/no-clobber creation where appropriate, attempts after-hash-guarded rollback after a partial failure, and records relative paths plus before/after hashes.
- Neither path automatically tests, initializes Git, stages, commits, pushes, publishes, or deploys.
- Returned executor failures use fixed safe messages rather than forwarding stderr.

## Workspace trust

Approved workspace seeds are authoritative one-time authorizations keyed by stable UUID, not folder name, path, or Git. Each seed contains canonical path, first-class filesystem identity, Codex reference evidence, aliases/history, permission policy, and optional Git top-level/logical-root/repository identity. Local-object identity v2 uses inode plus birthtime evidence and retains the current device number only as an observation, so device renumbering alone does not invalidate an object. Same-path root replacement, Git common-directory replacement, mixed legacy/v2 evidence, symlink substitution, and ambiguous candidates fail closed; legacy identity requires an exact reviewed migration. Project Brain is a normal candidate; repository-name and remote blacklists are not part of identity policy.

Valid narrow project references in Codex `config.toml` become onboarding signals only when trusted configuration explicitly enables `codex_projects.auto_onboard`. After canonicalization, directory validation, identity deduplication, ambiguity checks, and explicit-exclusion checks, new workspaces inherit the configured `permission_policy.allow_write`; the recommended private-plugin starting policy is read-only. With auto-onboarding disabled, the same metadata may still diagnose or reconcile an existing stable workspace but never admits a new one. Broad, missing, unsafe, ambiguous, or excluded references fail closed. Separately, explicitly approved narrow managed roots auto-onboard projects that have not appeared in Codex metadata under root policy. `/`, `/Users`, the user's home, drive roots, and common broad home containers are rejected. `create_project` still requires exact `CREATE`.

If a current path disappears, Bridge checks updated Codex references first (which may intentionally name a safe path outside managed roots), then searches only approved managed roots. It rebinds the same UUID only for one high-confidence filesystem and/or Git identity match and records the previous path. Folder name and root commit alone are insufficient. No match, multiple matches, an excluded workspace ID, or an unsafe destination fails closed. A directory that gains Git upgrades its existing identity in place. Reconciliation occurs on attach/use/request/explicit refresh; there is no workspace watcher.

The human reviewer must inspect every path and hunk in a proposal before supplying exact `APPLY`. A filename mentioned in a natural-language request is not a semantic file allowlist enforced by the code. Supervisor `accept` accepts read-only task output; it is distinct from `apply_controlled_patch` and does not write files.

## Persistence boundary

Two local state files provide restart persistence, both written atomically (write-temporary-then-rename) with mode 0600:

- `$STACK_ROOT/state/workspace-registry.json` — stable approved/managed workspace identities, aliases/path history, filesystem/optional-Git evidence, Codex references, and controlled-write policy. `$STACK_ROOT/state/<workspace-id>/` is the path-independent seam for durable project context, plans, decisions, and handoff snapshots. Individually invalid records are skipped on load; persist failures roll back the in-memory change.
- `<config>.controlled-patches.json` — controlled-patch proposals, routing/handoff audit metadata, and applied history. Invalid retained records are quarantined without blocking startup; duplicate identity, applied-history contradictions, and other global invariants still fail closed.
- `$STACK_ROOT/state/<workspace-id>/controlled-patches/<patch-task-id>.json` — bounded exact-preimage recovery material and relative-path/before-after-hash audit for directory or dirty-Git worktree operations, created only immediately before `APPLY`.

A reviewed migration that must replace both workspace config and registry uses the separate shared control-plane transaction helper. It derives both targets from the canonical stack root, rejects symlink/hardlink or insecure owner/mode ambiguity, persists exact preimage/result payloads plus a versioned mode-0600 journal, and syncs files and containing directories. A durable `COMMIT_INTENT` precedes either target replacement; after it, startup deterministically rolls exact pre/result states forward before parsing config or loading the registry. Unknown hashes, corrupt or competing journals, missing payloads, and terminal-state contradictions fail closed without overwrite. The same transaction lock excludes catalog registry persistence; no journal path can grant write authority outside the two derived targets.

The frozen identity-v2 operator entrypoint is a non-MCP command bound to one reviewed proposal ID, patch hash, two result hashes, and two immediate preimage hashes. It derives targets from the installed Bridge module path and accepts no target path. A mode-0600 process lease makes the running Bridge and migration mutually exclusive; a dead process lease is cleared only after PID liveness and file ownership/mode checks. The transaction writer lock independently excludes registry persistence. Runtime stop/restart is outside this command and remains a separate Owner-controlled operation.

These files are not a credential store and not a complete audit log. Active task supervision state (tasks, threads, evidence, review outputs) remains process-local and disappears on restart.

## Executor, state, and prompt boundaries

Codex's read-only sandbox and DSH's pinned read-only permission are the write boundary during tasks and proposal generation. They are not OS-level read jails: executors running as the same user may read other files allowed by the operating system.

Task results can include `review_output`, bounded command/file-change `evidence` (with explicit truncation markers when bounds apply), a real Codex `thread_id`, and `partial_output` from genuine interrupts. These records are review and diagnostic material, not a durable audit log or an additional write authorization mechanism.

The proposal-generation prompt constrains expected Git diff or filesystem-operation output but is not relied upon by itself; code validates the returned proposal before application.

## Not provided

Bridge provides no independent Web account authentication or public HTTP service, general resource quotas, automatic scientific acceptance, or replay of active tasks after restart. The original `run_task` supervision history remains process-local and has no automatic deadline; collaboration runs instead have durable manifests, declared artifacts and a deadline. Do not expose STDIO through an untrusted wrapper. Do not place credentials or sensitive material in prompts, configuration, or public reports.
