# Threat model

The development collaboration path adds opt-in writable scratch runs and durable manifests outside their writable roots. Declared inputs and outputs have bounded size/path/hash checks. Failures and interrupted restarts remain visible, and execution completion is distinct from accepted findings. This grants neither source-project writes nor publication authority. It provides no complete filesystem read isolation, CPU/GPU/memory quotas, or automatic dependency provisioning. Remote Web access must authenticate through its tunnel. The original V1 table below applies to the original task/patch paths.

Engineering Bridge Studio assumes one trusted local operator controls startup configuration and local MCP clients. Multiple sessions share one owner through a private Unix socket and token/nonce handshake; runtime and configuration identity mismatches require a clean restart. Read-only sessions retain their own capability boundary, and executor children cannot recursively delegate through Bridge. These controls do not defend against a hostile process running as the same OS user. Web authentication belongs to the remote tunnel. The following table retains the original V1 task and patch boundaries.

| Risk | Current control | Remaining responsibility or limit |
|---|---|---|
| Caller chooses an arbitrary workspace | MCP accepts only a registered ID; manual roots come from startup configuration, managed roots are confined to `project_root` approved roots | Operator must protect and review the configuration file |
| Onboarding accepts an unsafe project | Codex references are canonicalized, must be valid narrow directories, are deduplicated and checked against stable identity/exclusions; managed-root attach/create remains root-contained | Broad, missing, ambiguous, excluded, and unsafe candidates require human intervention |
| Executor modifies files during a task or proposal | `run_task`, supervisor continuations, steering, and proposal generation use fixed read-only settings: Codex approval `never` and read-only sandbox; DSH pinned `DSH_PERMISSION_MODE=read-only` per process | Same-user reads are not contained to the workspace |
| Caller text becomes a shell command | Codex app-server, DSH, and Git are started without a shell; instructions use the native protocol | Executors still interpret natural-language instructions |
| Environment secrets leak to the executor | DSH receives only an explicit allowlist (including `DEEPSEEK_API_KEY` and `DSH_TOOLS_MODE`); proxy variables are never forwarded | The allowlist itself is a deliberate surface; keep it minimal and reviewed |
| Supervisor action bypasses review state | `continue`/`accept` require `waiting_for_supervisor_review`; `steer`/`interrupt` require `running`; interrupt ends failed | The trusted supervisor decides whether output is acceptable and when to continue |
| Evidence or review output is treated as durable proof | `task_result` labels review output and returns bounded protocol evidence with task state; truncation/eviction by existing bounds is marked (`[truncated]`, changes-omitted counts, `evidence-drop`) | All such state is diagnostic material, not a durable audit record or semantic guarantee; markers only signal incompleteness |
| A proposal escapes through its path | Git parser retains strict path/entry checks; filesystem proposals reject absolute/traversal/non-normalized/duplicate paths and require canonical non-symlink parents/targets inside the root | Human must review all valid in-workspace targets and semantics |
| Workspace changes between review and apply | Clean Git retains exact base and `git apply --check`; dirty Git requires the same HEAD, a clean index, and exact current-worktree target preimages; directory/dirty-Git targets are immediately revalidated before each operation | Unrelated unstaged work is preserved; target/index drift fails closed, and a failed proposal may be retried only after preconditions are restored |
| Partial filesystem APPLY loses prior contents | Bounded 0600 recovery material is persisted first; atomic writes are used and earlier operations are automatically rolled back only when after-hashes still match | Recovery fails closed if another actor changes a partially applied target |
| Sensitive executor errors leak | stderr and partial failure output are discarded; fixed errors are returned; `partial_output` exists only for genuine interrupts and ordinary failures never re-expose it | Reduced diagnostic detail; no persistent redaction/logging system exists |
| Automatic publication occurs | Clean Git Apply uses only `git apply`; exact-preimage Apply uses fixed local file primitives and never changes the index; neither has test, init, add, commit, reset, stash, clean, checkout, push, publish, or deploy commands | User remains responsible for every later Git/publication operation |
| Restart loses durable state or observes a mixed control-plane migration | Controlled-patch proposals/applied history and the managed workspace catalog persist in mode-0600 state files; coordinated config/registry migrations use a synced commit-intent journal and complete deterministic recovery before either file is parsed | Active task supervision state (tasks, threads, evidence, review) is process-local and intentionally lost on restart |
| Retained state is corrupted or tampered with | State files are parsed strictly; individually invalid records are skipped/quarantined, while replay/applied ambiguity and global invariants fail closed | Files are not a credential store or a complete audit log; protect them like local configuration |
| Long-running task consumes resources | A running task may be explicitly interrupted through `control_task`, which ends it failed | No automatic timeout or resource quota is implemented |

Prompt wording improves proposal quality but is not treated as an enforceable control. Code validation and human review are separate and both necessary. `control_task` acceptance of read-only output is separate from the exact `APPLY` boundary that authorizes a validated controlled patch.
