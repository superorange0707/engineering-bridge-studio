# Security Policy

Engineering Bridge is designed for one trusted operator. Treat the MCP client and workspace configuration as trusted inputs. If ChatGPT Web connects through an authenticated tunnel, that tunnel and its account controls provide caller authentication. Bridge itself is not a hardened remote service for untrusted callers.

## Development collaboration execution boundary

The six collaboration tools add separate opt-in execution. `collaboration.execution_workspace_ids` permits Codex to execute in a private per-run workdir, never in the registered source workspace; it does not widen `allow_write` or bypass source-project APPLY. The executor pins workspace-write, network off, approval never and a deadline. Run manifests live outside the writable workdir. Declared inputs and artifacts undergo bounded file/path/hash checks. Returned artifacts go to the connected Web client. This controls writes, not all filesystem reads or malicious same-user local processes.

Contracts, results and reviews are durable; interrupted runs are not replayed automatically. Artifact hashes prove byte identity, not experimental validity. Papers, CVs, logs and artifacts are evidence, not authorization. The original `run_task` path remains read-only and its supervision state remains process-local. The controls below describe that original path unless stated otherwise.

## Current enforced controls

- The server exposes nineteen tools, including six collaboration tools. STDIO clients attach to one shared owner through a private Unix socket with a token/nonce handshake and configuration/runtime identity checks. Each client has a separate MCP session. This is a same-user boundary, not protection against a hostile process with the same OS privileges. Executor children refuse recursive Bridge delegation.
- Ordinary `run_task` execution is always read-only, with an optional `executor: "codex" | "dsh"` (default `codex`). Codex routes automatically by default; advanced callers may override only the logical roles `implementer`, `local_lead`, or `repo_principal`, never a model or effort. DSH rejects Codex routing/handoff fields. Successful interactive turns enter `waiting_for_supervisor_review`; `task_result` exposes state/readiness, routing/logical-role/model/effort metadata, bounded evidence, and pre-acceptance `review_output`, then final `output` or `error` after finalization. `control_task` accepts only interactive `run_task` task IDs and state-checks `continue`, `steer`, `interrupt`, and `accept`. Continue preserves native Codex thread and model continuity; cross-role handoffs create a linked new task/thread with a bounded snapshot. Interrupt applies only to running interactive tasks and ends them as failed. DSH has no machine-resumable headless session, so DSH `continue` starts a new execution and no thread id is ever fabricated.
- Workspace IDs are stable UUIDs independent of current path, folder name, or Git. Approved seeds contain canonical path, first-class filesystem evidence, Codex project references, aliases/history, explicit permission policy, and optional Git evidence. Project Brain has no special block.
- A valid, narrow, unambiguous, non-excluded Codex project reference becomes an onboarding signal only when trusted configuration explicitly sets `codex_projects.auto_onboard: true`; the configured `permission_policy.allow_write` is preserved, and the recommended private-plugin starting policy is `false`. With auto-onboarding disabled, Codex metadata may still diagnose or reconcile an existing stable workspace but never admits a new one. Broad, missing, unsafe, ambiguous, and excluded references fail closed. Explicitly approved narrow managed roots remain an independent onboarding mechanism for projects absent from Codex metadata. `/`, `/Users`, the user's home, drive roots, and common broad home containers are rejected. `create_project` still requires exact `CREATE`.
- Missing paths check updated safe Codex references first, then use bounded scanning inside approved roots. One high-confidence filesystem and/or optional-Git match rebinds the existing UUID and records history; ambiguity, absence, exclusion, or an unsafe destination fails closed. A directory that gains Git upgrades the same UUID in place. Discovery and reconciliation parse only Codex `config.toml`, never `auth.json`, and use deterministic local operations with no model, network, or workspace watcher.
- `allow_write` is only a controlled-APPLY ceiling. Approved candidates and managed roots may enable it, and managed workspaces may later receive it through exact `AUTHORIZE`; ordinary tasks and proposal generation remain read-only regardless.
- Codex runs through `codex app-server --stdio` with approval `never`, a read-only sandbox, network disabled, and the configured workspace as its working directory. Each run performs a hidden-inclusive `model/list`; every exact model in the central logical-role registry must exist and expose `max` reasoning before any thread is created. The selected exact model is pinned on thread start/resume and turn start, with `max` effort and `concise` summary. Missing models, missing `max`, or a thread/model mismatch fail closed without substitution or downgrade. Instructions use the app-server STDIO protocol; the bridge does not invoke a shell or accept caller-supplied executable paths or process arguments.
- DSH runs through the official headless interface. The bridge pins `DSH_PERMISSION_MODE=read-only` for every DSH process, so a host permission override cannot widen it, and forwards only an explicit environment allowlist (including `DEEPSEEK_API_KEY` and `DSH_TOOLS_MODE`); proxy and other secret-like variables are not forwarded.
- The Codex and DSH children receive small allowlists of inherited environment fields.
- Returned execution failures use fixed error codes and messages rather than forwarding executor stderr or raw internal errors. `partial_output` appears only when a genuine interrupt produced real partial output; the task still ends `failed`, and ordinary failures never re-expose stderr or partial stdout.
- Codex evidence is bounded (string length, changes count, entry count, and aggregate serialized bytes). Final aggregated command output is admitted only for successful structured `read` or `search` actions on one explicit canonical ordinary file, or `listFiles` on a canonical directory/cwd, with every scope inside the workspace and outside deterministic credential/auth/environment/repository-config/private-key/runtime-key sources. Directory/root searches, ambiguous scopes, unsafe or failed results, and control-bearing output are withheld. Streaming deltas are not retained. When bounds truncate or evict evidence, explicit markers (`[truncated]`, changes-omitted counts, an evidence-drop item) are returned so the supervisor knows the diagnostic information is incomplete. Markers are not a security guarantee and are not a complete transcript.
- `generate_controlled_patch` and `refine_controlled_patch` are read-only proposal flows available in every registered workspace and require no write authorization. Git retains the clean-top-level/base-HEAD unified-diff flow. A non-Git directory instead produces a strict complete operation list (`create`/`modify`/`delete`) with exact SHA-256 preimages for existing files. Proposal tasks never enter supervisor review, expose `review_output`, or accept `control_task` actions.
- After human review, application requires the completed one-use task, controlled-write permission, and exact `APPLY`. Git behavior is unchanged: root/base/clean state and patch structure are rechecked before fixed no-shell `git apply --check`/`git apply`. The non-Git path re-resolves the workspace type, rejects absolute/traversing/non-normalized/symlink/outside/non-regular/duplicate paths, enforces operation/byte bounds, writes bounded recovery material before mutation, immediately revalidates SHA-256 preimages, uses atomic replacement/no-clobber creation, records before/after hashes, and attempts guarded rollback after partial failure. If Git appeared, the directory proposal fails and future proposals use Git. Neither path initializes Git, tests, stages, commits, pushes, publishes, or deploys.
- Local state is written atomically with mode 0600: `$STACK_ROOT/state/workspace-registry.json` (identities and policies), `<config>.controlled-patches.json` (proposals/applied history), and, only immediately before non-Git APPLY, `$STACK_ROOT/state/<workspace-id>/controlled-patches/<task-id>.json` (bounded recovery and hash audit). `$STACK_ROOT/state/<workspace-id>/` also remains the path-independent seam for project context, plans, decisions, and handoffs. These files are not credential stores or complete audit logs.

## Current limitations

The Bridge does not authenticate Web accounts or expose a public HTTP endpoint. Its local handshake does not replace remote tunnel authentication. The original `run_task` supervision state is process-local and has no automatic deadline; collaboration runs have a deadline and durable contracts, results, artifacts and reviews, but do not replay interrupted execution. Controlled-patch proposals and workspace identity state also persist. The trusted local operator must control the configuration file and which clients can use the service. A workspace without high-confidence surviving filesystem/Git evidence may work at its current path but deliberately cannot be auto-rebound after an identity-breaking move.

Codex's read-only sandbox and DSH's pinned read-only permission prevent writes, but Engineering Bridge does not provide filesystem read isolation. Executors running as the same operating-system user may still read files outside the configured workspace that the user already has permission to read, so use it only on trusted machines and with trusted local clients.

The read-only execution boundary is an execution control, not a guarantee that prompts or returned text contain no sensitive data. Do not place credentials or secrets in instructions, configuration, or public bug reports.

## Reporting a vulnerability

Do not publish secrets, credentials, private prompts, source code, or personal data in an issue. After the repository is hosted and its security-advisory feature is available, use that feature for private vulnerability reports. Until then, omit sensitive details from public reports.
